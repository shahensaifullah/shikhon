# Project-wide backend internationalization

The `shared` app owns language middleware, catalogue discovery, translation and
the reusable DRF serializer mixin. Domain apps only own their own messages.

## Request language

`shared.middleware.ApiLanguageMiddleware` runs on every request:

```python
request.lang  # always "ban" or "en"
```

The query accepts `ban`, `bn`, `en`, and `eng`. Missing or invalid values default
to `ban`. Thus the frontend's existing `?lang=ban|eng` contract remains valid.

## Add translations to a new app

For an app named `lessons`, create:

```text
lessons/translations/
├── __init__.py
├── ban.py
└── en.py
```

`ban.py`:

```python
MESSAGES = {
    'lesson_created': 'পাঠ তৈরি হয়েছে।',
}
```

`en.py`:

```python
MESSAGES = {
    'lesson_created': 'Lesson created.',
}
```

`__init__.py`:

```python
from .ban import MESSAGES as BAN_MESSAGES
from .en import MESSAGES as EN_MESSAGES

TRANSLATIONS = {'ban': BAN_MESSAGES, 'en': EN_MESSAGES}
```

No central registration is required. `SharedConfig` discovers translation
packages from every installed Django app during startup and verifies that both
languages contain identical keys.

## Use a message

Use a namespaced key so variables never collide between apps:

```python
from shared.i18n import translate

detail = translate(request, 'lessons.lesson_created')
detail = translate(request, 'lessons.items_remaining', count=3)
```

The first argument is always the request. Unknown, missing, or ambiguous keys
raise a clear error instead of silently returning incorrect text.

DRF serializers can reuse the shared mixin:

```python
from rest_framework import serializers
from shared.serializers import LocalizedSerializerMixin


class LessonSerializer(LocalizedSerializerMixin, serializers.Serializer):
    def validate(self, attrs):
        raise serializers.ValidationError(
            self.msg('lessons.lesson_invalid')
        )
```
